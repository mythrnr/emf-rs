# AGENTS.md

A Rust library for parsing EMF (Enhanced Metafile) binaries and converting them to SVG.
Conforms to the [MS-EMF specification](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-emf/91c257d7-c39d-4a36-9b1f-63e3f73d30ca).

## Project Structure

The project is managed as a Cargo workspace with 3 crates.

```text
emf-rs/
  core/               # emf-core: EMF parsing & SVG conversion library (no_std)
  cli/                # emf-cli: CLI tool (example usage of emf-core)
  wasm/               # emf-wasm: WASM bindings (no_std, wasm-bindgen)
  docker/             # Development Docker environment
```

### emf-core (Main Library)

- `#![no_std]` compatible. Uses the `alloc` crate; I/O is abstracted via
  the re-exported `embedded_io::Read` trait.
- Depends on wmf-core (git dependency) for shared types (`RectL`,
  `PointL`, `ColorRef`, `Bitmap`, etc.) and WMF fallback conversion.
- Feature flags:
  - `svg` (default): SVG conversion (`SVGPlayer`)
  - `tracing` (default): log output (no-op macros when disabled)

#### parser Module (`core/src/parser/`)

Binary parsing that mirrors the MS-EMF specification's section
structure.

- `enums/` — Section 2.1 enumerations. Defined with `#[repr(u32)]` or
  similar, bidirectional conversion via `strum::FromRepr`, parsing
  generated by the `impl_parser!()` macro.
- `objects/` — Section 2.2 object definitions (`Header`, `LogPen*`,
  `LogBrushEx`, `XForm`, `EmrText`, ...).
- `records/` — Section 2.3 records, one directory per record category
  (bitmap, clipping, comment, control, drawing, escape,
  object_creation, object_manipulation, open_gl, path_bracket, state,
  transform).
- `primitive/` — primitive types such as `Size` (byte-count tracking).
- Key error types: `ParseError`, `ReadError`.
- Each record type has a
  `::parse(buf, record_type, size) -> Result<Self, ParseError>` static
  method.

#### emf_plus Module (`core/src/parser/emf_plus/`)

Parses EMF+ (MS-EMFPLUS) data embedded in `EMR_COMMENT` records whose
payload starts with the `"EMF+"` identifier (EMR_COMMENT_EMFPLUS).
The SVG converter consumes this module for bitmap playback; the
remaining record types are parsed but not yet rendered.

- Not re-exported flat from `crate::parser` (names such as `HatchStyle`
  would collide with EMF); always accessed as
  `crate::parser::emf_plus::*`.
- `enums/` — Section 2.1 enumerations (spec-verbatim variant names such
  as `BrushTypeSolidColor`) plus bit-flag newtypes in `flags.rs`
  (named mask constants and `contains()`).
- `objects/` — Section 2.2 graphics objects, structure objects, the
  image effects parameter objects with their identifier GUIDs, and
  `EmfPlusObjectData` (typed ObjectData dispatch).
- `records/` — Section 2.3 records, one directory per category. Record
  parsers mirror the EMF ones: the shape is
  `parse(buf, record_type, flags, size, data_size)`, the Type value is
  validated with `expect_eq`, and every record struct stores the
  common header fields verbatim in addition to decoded Flags
  sub-fields (`object_id`, `combine_mode`, ...) and the
  record-specific fields in wire order. `data_size` is a `Size`
  tracker bounding every read to the DataSize field. Rustdoc is
  transcribed verbatim from the MS-EMFPLUS record sections. There is
  no aggregate record enum: the consumer reads `EmfPlusRecordHeader`
  (`records/mod.rs`, which validates the header invariants),
  dispatches on the raw Type value in a `match`, then skips
  `padding_bytes()`. Unknown and reserved record types are the
  consumer's concern to skip.
- `object_assembler.rs` — `EmfPlusObjectAssembler` reassembles
  continued objects (the C flag of `EmfPlusObject`, data larger than
  64 KB) and yields `EmfPlusObjectData`.
- Point coordinates keep their wire encoding (`EmfPlusPoints`:
  absolute i16 / absolute f32 / relative EmfPlusPointR deltas) and
  normalize via `as_points_f()`; the same applies to rectangles
  (`EmfPlusRectData::as_rect_f()`).
- Hardening mirrors the EMF parser: `MAX_ELEMENT_COUNT` (16 Mi) bounds
  every count field via `check_element_count`, nested object sizes are
  bounded by `MAX_RECORD_BYTES`, and `EmfPlusRegion` limits its node
  tree recursion depth to 256.
- Known spec deviations (verified against GDI+ output, LibreOffice,
  Wine, libUEMF): `EmfPlusPath` treats relative points (0x0800) and
  RLE-compressed point types (0x1000) as independent
  `PathPointFlags` bits, every fragment of a continued object
  (including the final one with the C flag clear) starts with
  `TotalObjectSize`, and `EmfPlusBeginContainer` reads PageUnit from
  the low byte of the record flags (the specification diagram draws
  it in the high byte, but GDI+ writes the low byte like
  `EmfPlusSetPageTransform`). `CompositingQuality` uses the zero-based
  GDI+ enum (`Default=0x00 .. AssumeLinear=0x04`) rather than the
  0x01..=0x05 range in MS-EMFPLUS 2.1.1.6, because GDI+ writes the
  native value into `EmfPlusSetCompositingQuality` flags (Wine decodes
  `flags & 0xff` the same way); a real metafile therefore carries 0x00
  for the default quality.

#### converter Module (`core/src/converter/`)

Converts parsed records into an output format.

- `player.rs` — `Player` trait: one method per EMF record;
  `generate(self) -> Result<Vec<u8>, PlayError>` produces the final
  output.
- `emf_plus/bitmap.rs` — `DecodedBitmap`: decodes an EMF+ image object
  into BMP bytes for a player to embed. Covers the MS-EMFPLUS side of
  image playback: validates the 32-bpp pixel format, dimensions, and
  stride, normalizes the alpha channel to straight alpha, and
  serializes through the wmf-core DIB path. Player-agnostic: not gated
  behind the `svg` feature even though the SVG player is its only
  consumer so far.
- `emf_plus/player.rs` — `EmfPlusPlayer` trait: the EMF+ counterpart
  of `Player`, one `self`-by-value method per MS-EMFPLUS record, all
  defaulting to a no-op so a player overrides only what it renders. It
  is a separate trait an EMF+-rendering player opts into; an EMF-only
  player never implements it. `EmfPlusDispatcher` drives it: reads
  each `EmfPlusRecordHeader`, parses the record, reassembles continued
  objects (via `EmfPlusObjectAssembler`, delivering the typed
  `EmfPlusObjectData` to `emf_plus_object`), and folds the player
  through the matching method. The dispatcher is mechanical; the
  Dual/Only rendering policy lives in the player. It is not driven by
  the converter: a player that renders EMF+ owns an
  `EmfPlusDispatcher` and calls `play_comment` from its own
  `Player::comment`.
- `mod.rs` — `EMFConverter<B, P, WP>`: accepts a buffer
  (`embedded_io::Read`), an EMF player (`Player`), and a WMF player
  (`wmf_core::converter::Player`), then runs the conversion. The
  converter stays EMF-only: every `EMR_COMMENT` record goes to
  `Player::comment`, and the player decides whether the private data
  is an EMF+ comment (`is_emf_plus_comment`) and dispatches it.
  `run()` validates the input file signature and automatically falls
  back to the WMF player if the input is a WMF file, so the caller
  does not need to determine the format in advance.
- `playback_device_context.rs` — `PlaybackDeviceContext`: manages the
  graphics environment and transformation matrix. `EmfObjectTable`
  (object storage/retrieval), `SelectedObject` (currently selected
  brush/font/pen, etc.), `GraphicsObject` (enum of all creatable
  object types).
- `svg/` — SVG conversion implementation (when the `svg` feature is
  enabled):
  - `mod.rs` — `SVGPlayer` struct. Implements the `Player` and
    `EmfPlusPlayer` traits.
  - `svg_player.rs` — SVG generation logic for each record.
  - `node.rs` — SVG DOM node builder.
  - `util.rs` — Utilities for color conversion, coordinate transforms, etc.
  - `emf_plus.rs` — EMF+ bitmap state for `SVGPlayer`'s
    `EmfPlusPlayer` impl: stores bitmaps decoded by
    `emf_plus/bitmap.rs` as data URLs, emits the SVG image element on
    DrawImage, and suppresses all EMF+ drawing for Dual metafiles
    (their graphics are also described by EMF records, which the EMF
    path renders; an EMF+ Only metafile is rendered from its EMF+
    records). Only 32-bpp bitmap images are rendered so far.
- Error types: `ConvertError`, `PlayError`.

### emf-cli

- Single binary (`cli/src/main.rs`). Argument parsing with `clap` (see
  `--help` for the flags), log control via `tracing-subscriber` with
  `EnvFilter`.

### emf-wasm

- Single-file `#![no_std]` cdylib (`wasm/src/lib.rs`) exporting
  `convertEmf2Svg` and `setLogLevel` via `#[wasm_bindgen]`;
  `console_error_panic_hook` improves panic messages in the browser.
- Build artifacts land in `wasm/dist/` (default features) and
  `wasm/dist-minimal/` (no tracing); both directories are gitignored.
  Pushing a SemVer tag publishes them as `emf-wasm-<tag>.tar.gz` and
  `emf-wasm-minimal-<tag>.tar.gz` assets on GitHub Releases via
  `.github/workflows/release.yaml`.

## Coding Conventions

### Rust Style

- Formatted according to `rustfmt.toml` (`cargo +nightly fmt`):
  80-character lines including comments, nightly features.
- clippy: `all` + `pedantic` enabled at `warn` level; the specific
  allows live in the `[lints]` sections of the workspace and crate
  `Cargo.toml` files. `non_camel_case_types` and `non_snake_case` are
  allowed so identifiers can follow the specification record names
  (EMF record types keep their spec `UPPER_SNAKE_CASE`).
- Error definitions use the `snafu` crate; logging uses the `tracing`
  crate (disabled via feature flag).
- English only — no exceptions, not even temporarily during refactors —
  for all source comments (line, block, and doc comments in `.rs`,
  `.toml`, shell scripts, etc.), log messages, error messages, and
  identifiers. Do not mix languages within a comment block.

### Spell Check

- The cSpell dictionary lives in `.vscode/cspell.json`; when adding new
  EMF terms, add them to its `words` list.

## Testing

- Unit tests live in the modules they test; integration tests in

## Architecture

### Player Pattern

EMF record processing is abstracted via the `Player` trait:
`EMFConverter` sequentially parses records from a binary stream and
calls the corresponding `Player` methods. To add a new output format,
implement `Player` (and opt into `EmfPlusPlayer` if the format renders
EMF+). See the converter module notes above for the type parameters
and the WMF fallback.

### Binary Parsing

All data is read in little-endian byte order.

Field reads go through three internal helpers in
`core/src/parser/records/mod.rs`:

- `read_field<T>` — reads a fixed-width LE integer (selected via the
  `ReadLeField` trait, implemented for `i8`/`i16`/`i32`/`u8`/`u16`/`u32`/`f32`)
  and advances a `ConsumeTracker` (either `Size` or a plain `usize` counter).
- `read_with` — runs an existing `::parse(buf) -> Result<(T, usize), _>`
  helper and threads the byte count into the tracker.
- `read_bytes_field` — reads a variable-length byte buffer of `len` bytes
  and tracks the consumption.

Each parse function brings the helpers it actually uses into scope via a
function-scoped `use crate::parser::records::{...};` so call sites stay
short. Type annotations on `let x = read_field(...)?;` are dropped when
the type is pinned downstream by `expect_eq` / `expect_le` / `expect_ne`
(typed integer literal), `check_total_points` / `check_polygon_point_count_sum`
(both take `u32`), or struct-field shorthand on a typed field. When the
type cannot be inferred, the explicit annotation is kept.

### Hardening

- `Size::parse(byte_count_raw)` rejects record-size values past
  `MAX_RECORD_BYTES` (64 MiB) before any allocation is sized from them.
  `consume()` saturates on overflow and `remaining_bytes()` clamps to
  zero on overrun, surfaced via `is_overrun()`.
- `consume_remaining_bytes` discards the trailing record area in 4 KiB
  chunks instead of allocating a one-shot `Vec<u8>` of `remaining_bytes`.
- The multi-point drawing record parsers bound their point-count
  fields against `MAX_TOTAL_POINTS` (16 Mi points) via
  `check_total_points` before iterating. Multi-polygon records
  additionally validate that `polygon_point_count` entries do not
  overflow `u32` and do not exceed `count` via
  `check_polygon_point_count_sum`.
- The bitmap records reject `cb_bmi_src` / `cb_bits_src` (and the mask
  variants where applicable) when they exceed `MAX_RECORD_BYTES`,
  before the value drives `read_bytes_field`'s `Vec::with_capacity`.
- `ParseError::expect_eq` / `expect_le` / `expect_ne` give a uniform
  diagnostic format for field-value validation; hex width is selected
  from `size_of::<T>()`.
